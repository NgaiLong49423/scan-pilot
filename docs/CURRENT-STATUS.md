# Scan Pilot Current Status

## Current Phase

**Implementation stabilization and next-slice planning.**

The repository contains a working Spring Boot backend, a React dashboard connected to real REST reads, the `SP-CONFIG-001` scanning vertical slice, PostgreSQL/Flyway persistence, CI, and backend Cloud Run deployment. The application is not yet a complete continuous-monitoring product: the current frontend does not pass TypeScript lint, remote scans do not include full Git history, several UI metrics are simulated, scan execution is synchronous, and multiple accepted workflows remain specification-only.

The evidence-backed capability matrix and gap register is [Implementation Baseline and Gap Register](IMPLEMENTATION-BASELINE.md). Use it before decomposing or claiming feature completion.

- PostgreSQL/Flyway core schema and repositories.
- Manual scan trigger, remote working-tree snapshot acquisition, content classification, coverage persistence, secret detection, redaction, fingerprinting, finding lifecycle logic, and result APIs.

These are not equivalent to complete production readiness. See the implementation baseline for each limitation.

## Known Gaps and Contradictions

### Stabilization blockers

- Frontend TypeScript lint is red.
- Live terminal file events and intermediate counts are generated by timers rather than backend telemetry.
- MTTR, AI success rate, trend series, and some coverage fallback counts are static values while marked as real data.
- `Apply fix` changes React state only and can falsely present a Finding as `RESOLVED / VERIFIED_COMPLETE`.
- GitHub API failures can return development repository data instead of an explicit error outside a dedicated development profile.

### Core workflow gaps

- Remote GitHub zipball snapshots contain no `.git`, so complete reachable-history scanning is not available.
- `POST /scans/trigger` executes the pipeline synchronously; the documented asynchronous dispatch and polling flow is not implemented.
- Secondary branches are validated in memory but are not fully persisted and synchronized through GitHub default-branch events.
- Push, pull-request, merge, and scheduled scan triggers are not implemented.
- GitHub Issue creation from a Finding is not implemented.
- Repository Profile extraction, Review Request lifecycle, and Configuration Awareness remain incomplete beyond schema/research foundations.

### Documentation and contract gaps

- `DEC-060` is an accepted policy, not a description of current compliance.
- SRS and Use Cases describe target flows. They must be read with implementation status, not as completed behavior.
- `docs/requirements/SRS.md` is active; only `docs/requirements/PRD.md` remains a legacy template.
- `.agents/repo-contract.yml` still carries older phase/deprecation data and must be synchronized with this baseline.

2. Refine and execute Issue `#49` with an internally consistent Git-history coverage contract.
3. Introduce asynchronous scan job dispatch and real frontend job progress.
4. Harden production repository discovery/session behavior and persist branch configuration.
5. Add event-driven scan triggers.
6. Complete Finding-to-GitHub-Issue, Repository Profile, and Review Request vertical slices.
7. Execute Issue `#50` after UI strings and primary flows stabilize.
